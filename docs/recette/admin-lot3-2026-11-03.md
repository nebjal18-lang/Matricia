# Administration — lot 3 : recette native AAL2 et pagination

Branche `codex/admin-lot3-20261103`, après le lot 2 / PR #5. Candidat de code vérifié : `e37e76e`.

## Défaut reproduit et correction

Avec une vraie session administrateur AAL2 et peu de demandes d’approbation, l’ouverture du centre sur `actionPage=2` affichait une erreur générale de chargement. Les lectures autorisées et leurs contrats étaient valides ; la plage des approbations dépassait simplement les résultats. PostgREST retourne alors **HTTP 416 / PGRST103**. Le lecteur traitait cet état comme l’échec de toute la page, ce qui masquait également les tâches et le formulaire permettant de changer de filtre.

Le lecteur reprend la première page uniquement pour `PGRST103` sur une page supérieure à 1. Le statut, le tri, les colonnes et le client soumis à RLS sont identiques. Un refus, une autre erreur de lecture ou une réponse invalide restent des erreurs. Les contrats de lecture ont été regroupés dans un module pur, partagé avec la recette native, sans relâcher leurs contraintes.

## Recette réellement exécutée

Le nouveau harness `test:e2e:admin-native` crée quatre comptes temporaires par GoTrue : deux administrateurs AAL2 distincts, un propriétaire client AAL2 et un administrateur AAL1. Les facteurs TOTP sont réellement enrôlés et vérifiés ; aucun JWT AAL2 n’est forgé. Les rôles plateforme sont amorcés en SQL exclusivement pour ces fixtures locales : cela ne prouve pas le workflow de nomination d’un administrateur.

Le serveur Next compilé appartient au harness, qui enregistre son BUILD_ID, le commit du candidat, l’arbre applicatif et l’empreinte du harness. Un serveur tiers déjà présent n’est pas accepté comme provenance. Les origines et les conteneurs Supabase sont vérifiés comme locaux avant création des données.

**Résultat : 19 étapes natives PASS**, dont :

- Lecture et trois mutations refusées pour chacun des acteurs ordinaire, Admin AAL1 et anonyme ; versions et statut inchangés. Auto-approbation refusée.
- Six contrôles navigateur FR/AR des destinations attendues : espace autorisé, sécurité du compte avec retour Administration, ou connexion ; absence du titre de la tâche Admin dans la page refusée.
- Reproduction explicite du 416/PGRST103, puis récupération du centre et filtre conservant organisation/recherche en réinitialisant la page.
- Depuis le navigateur, prise en charge puis résolution **sans rechargement manuel**, confirmées par lecture indépendante en base. Une version historique est refusée. Parcours FR à 360 px et AR à 1 280 px.
- Rejet par le second administrateur depuis le navigateur FR à 1 280 px : formulaire remplacé par l’état courant sans rechargement manuel, statut REJECTED et version 2 vérifiés. Aucun effet métier de l’exception n’est exécuté.
- Nettoyage vérifié : **4 acteurs, 1 organisation**, zéro rôle/session/tâche ouverte/demande d’approbation en attente pour ces fixtures ; organisation archivée, faits immuables conservés et serveur arrêté.

## Fiabilité du harness historique

`final-admin-acceptance --probe` rend maintenant `PROBE_PASSED` et ne peut plus certifier un parcours navigateur non exécuté. Une fermeture de navigateur en erreur n’interrompt plus les neutralisations et suppressions suivantes. Les organisations dont le reçu HTTP aurait été perdu sont également découvertes via les adhésions des acteurs du run. Les étapes de nettoyage restent indépendantes ; toute erreur conserve le statut global FAILED. Les journaux sensibles restent privés et les résumés ne contiennent ni cookie, clé, secret TOTP ni erreur SQL brute.

## Limites précises

La base locale contient 229 versions enregistrées ; son empreinte est conservée dans la preuve. Ce lot ne certifie pas un rejeu neuf de toutes les migrations actuelles. Il ne modifie aucune migration, RLS, donnée distante ou configuration de production.

Le navigateur utilise HTTP loopback, alors que l’URL publique de métadonnées du build est HTTPS : les contrôles d’origine des API de fichiers/DSR ne sont pas exercés ici. Les scénarios ne constituent pas un visa du staging ni de tous les modules Admin. Les exécuteurs de confidentialité/effacement, gros exports et projections Boxes/crédits restent à compléter ou vérifier séparément.
